# Core backend: что готово и как проверить

Локальная ветка `feature/stage-1-core` основана на CRM PR #8 (`ff1da76`).
Изменения не опубликованы и не применены к общей БД. Аудит: [STAGE_1_CORE_AUDIT.md](STAGE_1_CORE_AUDIT.md).

## Реализованный backend Stage 1

- User, Department, Role, Permission, UserRole, RolePermission, ObjectPermission, Session, AuditLog.
- Связи Client/Deal/DealStageHistory/Activity с User; запрет физического удаления связанных пользователей.
- User.managerId, получение всех подчинённых, проверка циклов при смене руководителя.
- AuthUser `{id, roles, permissions}`, CurrentUser, JwtAuthGuard, RequirePermissions, PermissionsGuard.
- Login, короткий JWT (15 минут), случайный refresh token с хешем в Session,
  ротация через атомарную проверку старого хеша, logout/logout-all.
- При каждом запросе проверяются активность пользователя, сессия и актуальные права из PostgreSQL.
- PermissionService: базовое право отдельно от scope, явный DENY важнее ALLOW,
  свои/подчинённые/явно разрешённые объекты; фильтрация суммы сделки и вложенных секретных полей.
- Создание пользователя, смена статуса и руководителя, создание пользовательской роли,
  назначение ролей. Изменения сохраняются в одной транзакции с AuditLog.
- Socket.IO `/events`, персональные комнаты, проверка сессии перед каждой доставкой.
  Передаётся только уведомление об изменении объекта, без финансовых данных.
- BullMQ: очередь `crm`, повторные попытки и ограничение истории заданий.
- Минимальная Task с TaskParticipant и настраиваемым справочником статусов:
  NEW, IN_PROGRESS, REVIEW, DONE, CANCELLED. Это контракт данных для Stage 2.
- Activity.occurredAt сохранён обязательным: дата события отличается от даты записи.
- TOTP 2FA: зашифрованный секрет, подтверждение подключения, одноразовые резервные коды,
  ограниченный по времени challenge входа, защита от повторного использования OTP.
- Просмотр и отзыв сессий, смена пароля, административный сброс пароля с сохранением 2FA.
- Редактирование ролей, удаление неиспользуемых пользовательских ролей, управление ACL,
  подразделениями и профилями пользователей. Увольнение требует преемника при наличии
  активных клиентов, сделок, задач или подчинённых и передаёт ответственность транзакционно.
- Файлы в S3: загрузка до 25 MiB, неизменяемые версии, скачивание через backend,
  безопасное превью изображений/текста, личные папки, переименование, связи с объектами,
  мягкое удаление. ACL и права всех связанных объектов проверяются при каждом чтении.
- Inbox уведомлений, настройки каналов, идемпотентность по userId/eventKey,
  транзакционная очередь доставок с повторами, SMTP/Telegram/FCM-транспорты.
- Просмотр и экспорт аудита с отдельными правами, единый формат ошибок API,
  Swagger со схемами DTO. Пользовательские поля фильтруются по CustomFieldDefinition.

## Проверки

Из `backend/`:

```powershell
npm ci
npm run prisma:validate
npm run typecheck
npm test -- --runInBand
npm run test:migrations
npm run test:core-integration
npm run lint
npm run build
```

59 модульных тестов дополняются проверкой всех миграций в PGlite. Сквозной тест запускает
настоящий Nest HTTP и Prisma поверх локального PostgreSQL-протокола PGlite: вход,
роли, 2FA и повторы кодов, версии файлов, DENY, inbox и увольнение с преемником.
В этом тесте S3 и очередь заменены; отдельный тест проверяет настоящий AWS SDK на локальном
HTTP-хранилище. Оба теста изолированы и не используют общую DATABASE_URL.
PGlite не заменяет полноценный PostgreSQL для проверки конкурентных транзакций.

Для подготовленной отдельной инфраструктуры есть `npm run test:infrastructure`.
Он требует явного `RUN_CORE_INFRASTRUCTURE_TESTS=1` и переменных
`CORE_TEST_DATABASE_URL` (имя базы заканчивается `_core_test`), `CORE_TEST_VALKEY_URL`,
`CORE_TEST_S3_ENDPOINT`, `CORE_TEST_S3_BUCKET` (заканчивается `-core-test`),
`CORE_TEST_S3_ACCESS_KEY`, `CORE_TEST_S3_SECRET_KEY`.
База должна иметь применённые миграции, bucket должен существовать. Скрипт не читает `.env`.
Он проверяет конкурентную ротацию сессии, выполнение задания BullMQ и S3 upload/read/delete;
удаляет только собственные тестовые записи, объект и очередь с уникальным префиксом.
После установки Docker Desktop 4.89.0 / WSL 2.7.12 и перезагрузки тест успешно выполнен.
Все 4 миграции применены через `prisma migrate deploy` к отдельной пустой базе.
Проверены конкурентный Session CAS (ровно один победитель), настоящий BullMQ Worker
на Valkey и S3 upload/read/delete с подтверждённым NoSuchKey после удаления.
Использованы образы проекта: pgvector/pgvector:0.8.6-pg17, valkey/valkey:9.1.1-alpine,
chrislusf/seaweedfs:4.44. Полный HTTP-сценарий выше по-прежнему использует PGlite.

Стенд описан в `backend/test/compose.infrastructure.yml`. Перед запуском задать случайный
`CORE_TEST_PASSWORD`, затем из backend выполнить
`docker compose -f test/compose.infrastructure.yml up -d --wait`.
PostgreSQL доступен на 127.0.0.1:55432 (core_test, база bigproject_core_test),
Valkey — 127.0.0.1:56379, S3 порт определяется через
`docker compose -f test/compose.infrastructure.yml port seaweedfs 8333`.
S3 access key — core-test, bucket — bigproject-core-test; пароли равны CORE_TEST_PASSWORD.
Заполнить CORE_TEST_* выше, установить DATABASE_URL равным CORE_TEST_DATABASE_URL,
применить миграции и выполнить test:infrastructure. После проверки удалить только этот
стенд: `docker compose -f test/compose.infrastructure.yml down --volumes`.

Реальный запуск выявил и исправил путь миграций в prisma.config.ts: при разнесённой схеме
папка migrations теперь указана явно. Без этого CLI не находил SQL-файлы.
В данной сети Docker Hub давал TLS handshake timeout; образы скачаны с проверкой
сертификатов по TLS 1.2, проверены SHA-256 слоёв и импортированы в Docker.

## Первый локальный запуск на НОВОЙ базе

1. Подготовить Node 24, Docker Desktop и `.env` по DEVELOPMENT.md.
2. Заменить `JWT_ACCESS_SECRET` на случайный секрет длиной минимум 32 байта.
   Значения `change_me` приложение отклоняет. Секрет нельзя коммитить.
   Для 2FA настроить `TOTP_ENCRYPTION_KEY`: 32 случайных байта в hex (64 символа).
   Не менять этот ключ без переноса зашифрованных секретов. Секрет подключения и резервные
   коды выдаются один раз защищённым endpoint; ответы имеют Cache-Control: no-store.
3. Запустить инфраструктуру `docker compose up -d` из корня репозитория.
4. Из `backend/` выполнить:

```powershell
npm ci
npm run prisma:migrate
npm run core:seed
npm run start:dev
```

`core:seed` создаёт каталог прав и системные роли. Он не создаёт пользователя с общим
паролем и не перезаписывает права существующих ролей. Начальные права — консервативный
набор для первого объёма; SALES_MANAGER не получает `deal.field.amount.read`.

Для первого владельца дополнительно передать `CORE_BOOTSTRAP_EMAIL` и
`CORE_BOOTSTRAP_PASSWORD` через локальное окружение и повторить `core:seed`.
Создание владельца разрешено только при пустой таблице User. Пароль минимум 12 символов.
После создания убрать эти переменные из окружения. Они не используются при обычном старте.

## Если CRM-база уже создана через db push

НЕ запускать миграции вслепую. Сначала сделать резервную копию и проверить схему.
Первая миграция `20260903090000_crm_baseline` описывает ровно исходную CRM-схему PR #8.
Только после подтверждения полного совпадения её можно отметить как уже применённую
через `prisma migrate resolve --applied 20260903090000_crm_baseline`.
Это не команда для новой или частично совпадающей БД.

Если CRM уже содержит записи с responsibleUserId/changedById/userId, нужно сначала
согласовать перенос реальных пользователей с теми же UUID. Миграция с внешними ключами
правильно остановится на ссылках на отсутствующих пользователей. Заглушки-пользователи
автоматически не создаются, существующая история не удаляется.

## Контракт для CRM

Импортировать `AuthModule`, `PermissionsModule`, `AuditModule`, `UsersModule`,
`EventsModule`, `QueuesModule` в модуль потребителя по необходимости.

1. `@RequirePermissions('deal.read')` вместе с `PermissionsGuard` проверяет только базовые права.
2. `PermissionService.canAccessObject(user, 'deal.read', {id, type:'DEAL', responsibleUserId})`
   проверяет scope/ACL. Передавать данные объекта из БД, никогда из тела запроса.
3. Списки фильтровать ДО пагинации и подсчёта total: отдельно учитывать DENY/ALLOW.
   `getAllowedScope()` даёт только организационную часть, не готовый фильтр ACL.
4. Перед API-ответом вызвать `filterFields(user, 'deal', dto)`. Прямой возврат Prisma include
   без проверки родительского/связанного объекта недопустим. Пользовательские поля требуют
   вызова `filterCustomFields()`, который проверяет CustomFieldDefinition.fieldCode.
5. `AuditService.log(entry, tx)` писать в транзакции изменения. Не передавать токены/пароли.
6. После успешного commit вызвать
   `emitToUsers(authorizedUserIds, 'deal.updated', {entityType:'DEAL', entityId, action:'updated'})`.
   Получатели вычисляются CRM через PermissionService. Payload с суммой не пересылается.
7. Очередь доступна через `@InjectQueue('crm')`. Обработчики задач и идемпотентность — в CRM.
   Для Worker использовать отдельное подключение с `maxRetriesPerRequest: null`.
8. `Deal.nextActionAt` не FK. Искать Task по `dealId`, `deletedAt:null`,
   `taskStatus.isTerminal:false`; пересчёт даты/описания — ответственность CRM/Tasks.
9. Activity всегда получает фактический occurredAt. Не подменять его временем импорта.
   Пересчёт lastContactAt/lastActivityAt должен учитывать поздние события через максимум,
   а не безусловную запись даты последнего импорта.

## Границы и эксплуатационные условия

Это backend; экраны управления остаются задачей frontend.
Task API, бизнес-переходы, история дедлайнов и Project FK принадлежат Stage 2/3.
ObjectAccessService уже разрешает TASK/CLIENT/DEAL/FILE; будущие домены должны зарегистрировать
свой resolver/policy. Неподдерживаемые типы закрыты по умолчанию.

Внешняя доставка выключена по умолчанию (`NOTIFICATION_DELIVERY_ENABLED=false`). Для неё
нужны SMTP, Telegram bot или Firebase/Google ADC и настроенные администратором адресаты.
Реальные сообщения в ходе работы не отправлялись; внешние аккаунты не проверены.
Транспорт передаёт нейтральный текст без бизнес-полей, перед отправкой повторно проверяет
активность и права адресата. Доставка at-least-once: сбой после приёма провайдером может дать
повтор. Администратор видит FAILED/SKIPPED и может повторить доставку.

Папки личные; доступ к файлу выдаётся через ACL или связанный объект. Неизвестные форматы
доступны только как вложения. Мягкое удаление сохраняет историю. При отказе и БД, и удаления
S3-компенсации возможен объект без записи: он отмечается в журнале для сверки хранилища.

Расширения модели для ревью команды: securityVersion/AuthChallenge и поля 2FA,
FileFolder/FileVersion, NotificationDelivery/NotificationPreference/eventKey и notification.manage.
Они не означают автоматическое согласование 11 предложений CRM из PR #8.

Сейчас Events рассчитан на один экземпляр backend. Горизонтальное масштабирование требует
Redis adapter; ограничение частоты запросов тоже пока локальное на экземпляр.
JWT_ACCESS_SECRET обязателен; JWT_REFRESH_SECRET не используется, поскольку refresh token
не JWT. Событие отправляется после commit без гарантии доставки: для надёжной доставки
нужен outbox у соответствующего бизнес-производителя; Notifications уже имеет свой outbox.
CRM API из PR ещё отсутствует, поэтому полную CRM-сборку
и поведение экранов нельзя считать проверенными.

Перед PR в develop согласовать с автором #8 порядок слияния и 11 предложений CRM.
Если #8 будет squash/rebase-слит, перенести только Core изменения на новый develop.
Не отправлять всю зависимую историю как независимый Core PR без проверки diff.
